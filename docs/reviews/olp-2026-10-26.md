# OLP, reviewed · 26 October 2026

**What was reviewed:** OLP's handbook (sources/olp/olp-handbook.html),
which covers Odoo 17.0 to 20.0 and prov-api schema V77, and says its
version numbers, paths and permission codes were read from the running
system. **Not reviewed:** OLP's code, its running system, its tests, its
hosting, or a security test of it; every finding is the handbook's
account, to confirm with OLP's owners.

**What this is:** a review of OLP as it stands, by Financial Services,
for OLP's owners and for us. What Financial Services needs from OLP is
not here: it is the [OLP spec](../specs/olp.md), whose needs (N1 to N14)
cite the gaps below (G1 to G9). OLP is Dibon's, and an independent
component with its own roadmap (FS-973).

## 1 · What OLP is

A dashboard and four services that run Odoo sites: each site an Odoo in
Docker with its own database on a shared PostgreSQL, behind nginx with
HTTPS, on a machine OLP hosts or one the customer brings (DigitalOcean,
Vultr, AWS, or any server over SSH). It provisions with Terraform and
Ansible, then shell scripts over SSH; it adds modules from Git, attaches
domains, makes staging copies, backs up on a schedule, restores, imports
sites from other hosts, and upgrades Odoo a major version at a time.
Its own services run on k3s: identity and billing (Spring Boot, MySQL),
provisioning (Spring Boot, PostgreSQL), backups and migrations (Node),
notifications, and a React dashboard.

## 2 · Strengths

1. **Upgrades are safe by construction:** one major version at a time,
   on a staging copy, production serving throughout; promote when
   satisfied, roll back to the original, or discard the copy.
2. **Restores are careful:** a backup restores only into its own Odoo
   major version, a snapshot is taken before anything is overwritten,
   and a destructive act asks for the target site's name to be typed.
3. **Staging returns code, never data,** and a production site cannot be
   deleted while a staging copy of it exists.
4. **Tenancy and permissions:** every query scoped to the organisation;
   another organisation's resource reads as absent, not forbidden; doors
   check permission codes, not role names; senior roles include junior
   ones by construction; deletion is the owner's.
5. **Honesty in what it shows:** an Enterprise expiry no Odoo
   subscription could have is "Unverified"; a suppressed alert is
   recorded as suppressed; removals are audited and alerted with the
   person's name.
6. **Add-ons from Git,** with each module's Python packages declared and
   installed before Odoo loads them; Enterprise add-ons supplied once per
   major version.
7. **Edition switching** between Community and Enterprise.
8. **Work runs on the customer's machine,** scripts streamed over SSH,
   so OLP keeps no copy of a site's data in transit, and a backup goes
   from the server straight to its destination.
9. **A scheduler that catches up:** a late tick still fires, a double
   tick fires once, a missed hour is caught up.

## 3 · Gaps

| Id | Gap | Why it matters | Severity |
|---|---|---|---|
| G1 | Upgrades run OpenUpgrade only, which migrates Community and OCA modules, not Enterprise's own apps (Sign, Helpdesk, Documents) | An Enterprise site cannot be upgraded through OLP with those apps intact; Odoo's own upgrade service is the supported path for Enterprise | High |
| G2 | One deployment model: Odoo in Docker on a machine, a PostgreSQL container shared by the sites on it, files on the machine | No synchronous database standby or replicated file storage; no way to run inside a Kubernetes platform | High, for regulated or high-availability use |
| G3 | No hook before promotion | A customer's own tests cannot gate a promoted upgrade or staging copy | Medium |
| G4 | OLP's own sign-in (passwords, two-factor, social login), not a central identity provider | Users and engineers managed apart from the rest of Dibon's access; no hardware-key requirement for powerful rights | Medium |
| G5 | Where the SSH keys that reach every managed server are kept, and how their use is recorded, is not stated | The most powerful thing OLP holds | High, until stated |
| G6 | Backup encryption, the location of platform storage, and FTP as a destination are not addressed | Backups of business and personal data | High, until stated |
| G7 | Terraform for provisioning | Terraform is now under the Business Source License | Low to medium |
| G8 | Generated admin passwords shown once, to be copied | Secrets end up where people keep them | Medium |
| G9 | One token secret shared by four services | A leak of it forges tokens for all four | Medium |

**Smaller points:** alerts are off until an organisation turns each on,
so a new organisation is silent; a webhook can deploy add-ons on every
push to a branch; the handbook names no hosting in Kenya yet.

## 4 · What the handbook gets right that others could borrow

The upgrade procedure (§2.1), the restore guards (§2.2), absent-not-
forbidden tenancy (§2.4) and "Unverified" (§2.5) are patterns Financial
Services' own specs adopt or cite (back-office §9, FS-971).

## 5 · Corrections to Financial Services' documents

- **Business suite BS-11** says OLP's upgrades are built: true for
  Community; Enterprise's are G1.
- **The portfolio** says OLP is hosted in Kenya: the handbook names no
  Kenyan hosting; it is planned on Liquid's Azure Stack. *Answered
  2026-10-27 (FS-986): the sites OLP deploys for our clients are hosted
  in Kenya, so the claim stands; the correction was undone.*
