## 1 · The current CI/CD

One pattern, in GitHub Actions on GitHub's hosted runners:

```
  +--------------------------+      +--------------------------+      +--------------------------+
  | GITHUB                   |      | HOSTED RUNNER            |      | K3S SERVER               |
  | a push to a branch       |--1-> | finds what changed,      |--2-> | kubectl sets the new     |
  |                          |      | tests, builds, pushes    |      | image; undone if it      |
  | main: production         |      | to GitHub's registry     |      | does not become ready    |
  | dev: a dev environment   |      | by tag                   |      |                          |
  +--------------------------+      +--------------------------+      +--------------------------+
                                                  |
                                                  | 3
                                                  v
                                    +--------------------------+
                                    | MESSAGES                 |
                                    | each stage to the team   |
                                    | on WhatsApp              |
                                    +--------------------------+
```

1. A push to main (or dev) starts the workflow.
2. The runner reaches the server over SSH with a key held as a GitHub
   secret, and swaps each changed service's image.
3. Started, tested, built, done or failed, each as a message.

**The repositories using it:**

| Repository | What it deploys | Shape of its pipeline |
|---|---|---|
| odoolaunchpad | OLP, Dibon's Odoo platform: four services and a dashboard | Tests on every branch and pull request; dev and production workflows; the dashboard deployed in a job of its own. The more developed of the two: most practices in §2 are its own |
| kapu-pay | Kapu Pay: six Java services, two Node services, the portals and an internal tool | One workflow, production only, built after odoolaunchpad's dev workflow, as its header says |

The pattern is not the one the GitHub spec describes: we pull with
Flux, from Harbor, signed images admitted by Kyverno, runners in Kenya
(flows §4). What follows holds in either.

## 2 · What to adopt

Each practice came from a failure met while running the current CI/CD,
and written into its workflows. **Neither** the GitHub spec and flows
**nor** Max's folder says it; where one comes close, the column says so.

| # | Practice | Where it came from | Closest today |
|---|---|---|---|
| P1 | Migrations tested against a real database set like production | A migration passed locally and failed on the managed database, which requires primary keys; another time entities drifted from the schema and a pod would not start | Testing §3: integration tests against PostgreSQL in a container; not the migrations, in order, on production's settings |
| P2 | An applied migration is never edited | A migration was edited after production applied it; the checksum no longer matched and the service crash-looped on deploy | PostgreSQL S14: schema changes only through migrations; not their immutability |
| P3 | Evidence kept before a rollback | Two failed deploys were diagnosed by guesswork: the rollback removed the pod, and its log with it | Flows §4: "a step back is a revert"; Max: rollback by Helm's atomic flag |
| P4 | An environment is built on its own, never from production's settings | A dev environment never created; copying production's secrets would have pointed a dev build's migrations at the production database | GitHub §4.5: production's secrets only to its branch |
| P5 | No pipeline left permanently red | A dev rollout failed on every push for a known reason; a build always red teaches the team that red means nothing | None |
| P6 | Each deploy its own unit, with a timeout | A frontend upload hung for two and a half hours and held every backend deploy behind it, with no error, only silence | Max: a five-minute timeout on Helm |
| P7 | A failed deploy is retried, not lost | Change detection diffed against the previous push, so a release lost to another service's failure was never rebuilt, and stayed stale for weeks | None |
| P8 | What is live is checked, not assumed | "Is it deployed?" kept coming up; the pipeline reported the deployment, not what the domain served | Site failover's smoke tests, after a failover only |
| P9 | Messages say what happened | A failure message claimed a rollback when nothing had been rolled out, sending people after a regression that did not exist | GitHub §8: workflow events to the team's channel |
| P10 | A blocking check for each kind of failure that reached production | A misplaced React hook shipped a blank page past a green suite; a one-rule lint now blocks it, added at zero violations | Max: linting in general |
| P11 | Tools installed by a job pinned to an exact version | A deploy tool is installed at a pinned version, since a new major can change behaviour under an untouched workflow | GitHub §4.4: actions by commit, images by digest; not tools a job installs |

### P1 · Migrations tested against a real database, set like production

- **What:** every pull request that touches a service applies its
  migrations, in order, to a throwaway PostgreSQL, then starts the
  service against it, so the ORM validates its entities against the
  schema the migrations produced. A mismatch fails the pull request,
  not the pod.
- **Set like production:** the throwaway database runs the version and
  the settings of the [PostgreSQL baseline](../settings/postgresql.md)
  that affect what a migration may do, as the current CI/CD sets its
  database's primary-key requirement for exactly this reason.
- **Where it lands:** testing §3, within integration tests, and the
  shared workflows (GitHub §4.4).

### P2 · An applied migration is never edited

- **What:** a migration file already on main is never changed; a fix is
  a new migration. A required check fails a pull request that alters
  one, comparing it with main.
- **Why here too:** the ledger's and the services' schemas change only
  through migrations (PostgreSQL S14), and a checksum mismatch stops a
  service at start, mid-release. On a ledger that means safe mode.
- **Where it lands:** the shared workflows, and ways of working's git
  conventions.

### P3 · Evidence kept before a rollback

- **What:** when a new version fails its health checks, its pods'
  status, events and logs, including the previous container's log of a
  crash-looping pod, are kept before anything is undone.
- **In our model:** Flux and the rollout undo nothing until told; Loki
  keeps pod logs. What is missing is the link: a failed rollout's alert
  names the release and opens the logs of its pods, current and
  previous, and the events, for the window of the rollout.
- **Where it lands:** observability's alerts, and a deploy-failure
  runbook (open question 2).

### P4 · An environment is built on its own

- **What:** each environment has its own database, secrets and
  hostnames from the start. A deploy first checks that its target
  exists and refuses, saying why, if it does not; it never creates one
  on the way.
- **The rule:** no environment's settings are copied from production's.
  In platform, a stage's folder names only its own stage's paths in
  OpenBao and its own database; a check refuses any staging or dev
  values that name a production secret path or database host.
- **Where it lands:** GitHub §4.5 and §6 (platform's folders), and the
  settings README.

### P5 · No pipeline left permanently red

- **What:** a job that cannot pass for a known reason, such as an
  environment not yet built, is switched off by a recorded setting and
  shows as skipped, with the reason in the workflow; its tests still
  run. A required check is never left failing past a working day: it
  is fixed, or switched off by a register row.
- **Why:** a build always red is ignored, and then a real failure is
  waved through.
- **Where it lands:** ways of working, beside required checks.

### P6 · Each deploy its own unit, with a timeout

- **What:** deploys that share nothing do not share a queue. Each
  service's deploy has its own concurrency group; production deploys
  queue and are never cancelled; previews and other superseded builds
  are cancelled by the newer one. **Every job states a timeout**: a
  hosted job otherwise holds its runner for six hours.
- **In our model:** each service its own Flux Kustomization with its
  own timeout, so one stuck service holds no other.
- **Where it lands:** the shared workflows, and platform's layout.

### P7 · A failed deploy is retried, not lost

- **What:** what to deploy is decided by comparing what should run with
  what runs, never by what changed since the previous push. A manual
  "redeploy everything" stays as the recovery, as kapu-pay has one.
- **In our model:** Flux compares the manifest with the cluster on every
  reconcile, so a release that failed is tried again until it succeeds
  or is reverted; a forced reconcile is the manual recovery. Keep it
  so: no workflow that pushes into a cluster on a diff.
- **Where it lands:** a sentence in flows §4.

### P8 · What is live is checked, not assumed

- **What:** after each rollout, a check asks the running service for its
  version (a version endpoint giving its image digest) through the
  public address, compares it with the release, and runs the release's
  smoke tests.
- **Where it lands:** flows §4, step 5; each service's spec, a version
  endpoint; the smoke tests from site failover reused for every release.

### P9 · Messages say what happened

- **What:** a deploy message says exactly what changed: "rolled back to
  version X" only when something had rolled out; "nothing changed" when
  the deploy stopped before it. Started, done and failed, each with the
  release and a link to its run.
- **Where it lands:** GitHub §8, with the team's channel once chosen
  (FS-759).

### P10 · A blocking check for each kind of failure that reached production

- **What:** when a defect of a kind tests could have caught reaches
  production, its incident review adds a check that blocks that kind of
  defect, introduced when nothing violates it, so it blocks nothing that
  works.
- **Where it lands:** incident management's review step, and the shared
  workflows.

### P11 · Tools a job installs, pinned to an exact version

- **What:** command-line tools a job installs (from npm, a package
  manager or a download) are pinned to an exact version, and moved by
  Renovate like any dependency (GitHub §9).
- **Where it lands:** technology's pinning rule, extended from actions
  and images to the tools a job installs.

## 4 · Seen and not adopted

| What the current CI/CD does | Why not here |
|---|---|
| Tests as information only (kapu-pay everywhere; odoolaunchpad on dev) | A test that fails blocks the pull request (GitHub §4.2) |
| Deploys pushed into the cluster over SSH with kubectl | Flux pulls; nothing in GitHub reaches into a cluster (GitHub §2) |
| Images in GitHub's registry, by tag | Harbor, by digest, signed (flows §4) |
| A frontend image built per environment, its addresses baked in | One image promoted from staging to production, never rebuilt (GitHub §6), so its addresses are read when it starts |
| An image loaded onto the server by hand because the cluster could not pull it | Every image from Harbor, at every site |
| SSH keys and service tokens stored as GitHub secrets | Secrets from OpenBao with a short-lived token (GitHub §4.4) |
