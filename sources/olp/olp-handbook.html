Part one — Using OdooLaunchPad

What OdooLaunchPad is

A place to run Odoo without running servers. You get a site with its own address and HTTPS certificate, backed up on a schedule, with a staging copy when you need one.

Everything you create is an Odoo site: one Odoo application with its own database, its own address, and its own add-ons. Sites live on servers. You do not have to own a server — that is the first choice the product asks you to make, and it is the only one that is hard to change later.

Launch — on our hosting

Pick what you need and we put the site on infrastructure we already run. Nothing to install, no cloud account, no server to look after. This is the quick path.

Your own server

Rent a machine from DigitalOcean, Vultr or AWS through your own account, or connect one you already have over SSH. We install Docker, PostgreSQL, nginx and the certificates, then keep it monitored. The machine stays yours.

Both end up with the same thing running: Odoo in a Docker container, a PostgreSQL database beside it, and nginx in front terminating HTTPS. The difference is who owns the machine and who pays the cloud provider.

Your first site

From a new account to a site you can sign in to.

If you want us to host it

  1. Open Launch in the sidebar. This is the only route that assumes nothing about servers.
  2. Choose what you want, confirm the address, and pay. The address is yours on our base domain, and you can attach your own domain later.
  3. Wait. The page tracks the build: the server is readied, the database is created, the certificate is issued. It moves itself along — you do not have to press anything.
  4. When it finishes, the page shows the link and the admin password. Copy the password somewhere safe; it is how you first sign in to Odoo.

If you are bringing your own server

  1. Connect a cloud account under Settings → Cloud, or have the server's SSH key ready. DigitalOcean connects by OAuth; Vultr and AWS take an API key.
  2. Add a server from the Servers page. Choose the provider, region and size, or pick Connect over SSH for a machine you already have. Provisioning installs Docker, PostgreSQL, nginx and certbot and takes a few minutes.
  3. Add a site from that server's page. Name it, pick the Odoo version and edition, and keep the admin password it generates.
  4. Point your domain at the server, or use the address we give you. See Domains and HTTPS.

The name becomes the address. A site named bright-compass is reachable at bright-compass.<your base domain> as soon as it is running. Pick something you will recognise in a list of twenty.

The Sites page lists everything you run, with staging copies nested under the site they came from.

A row marked Staging and indented under another site is a copy of that site, not a separate one. See Staging.

Starting, stopping, deleting

Stopping a site stops the container. Nothing is lost and it costs you nothing in storage; it simply does not answer. Deleting is different: it removes the database and the files, and it cannot be undone. You will be asked to type the site's name to confirm, because the name on the screen above the box is not enough to stop a mis-click on the wrong row.

Before you delete

Take a backup first if there is any chance you want the data. A deleted site's database is gone from the server — the only copy left is whatever backup you already took.

Editions and licences

Community is free. Enterprise is Odoo's paid product, and only Odoo can say whether your database is covered.

The two editions

Community is the open-source Odoo. It needs no subscription, has no expiry, and a Community database carries no licence state at all. Enterprise runs the same Odoo with Odoo's paid add-ons layered on top of the add-ons path. Those add-ons require a subscription bought from Odoo.

Registering a subscription

Enter your subscription code either in Advanced options when creating the site, or on the site's page afterwards. The code goes into the database as database.enterprise_code and Odoo validates it against odoo.com — the same thing Odoo's own "Activate your subscription" screen does. The expiry shown back to you is Odoo's answer, not ours.

What you seeWhat it means
LicensedOdoo accepted the code and gave an expiry a subscription could plausibly have.
Ends in N daysWithin 30 days of expiry. Renew or it stops serving.
ExpiredThe date has passed.
Code rejectedA code was entered and Odoo refused it. Check the code and register it again.
No licenceNothing has been registered. Odoo gives a new Enterprise database a short trial; enter your code before it ends.
UnverifiedThe expiry is set further out than any Odoo subscription runs, so it cannot be confirmed.

Why "Unverified" exists. The expiry is a row in the database, and anything able to write to that database can put any date in it. A date decades out was not sold by Odoo, so the platform reports it as unconfirmed rather than repeating it as though Odoo had vouched for it. Sites brought in from other hosts often arrive this way.

Supplying the Enterprise add-ons

Enterprise add-ons are files, and the platform needs a copy. Under Settings → Enterprise you can give either a private GitHub repository with a token, or the odoo_<version>+e.<date>.tar.gz archive Odoo gives subscribers. One source per Odoo major version. The first Enterprise site of a version on a server installs them; every later one on that server reuses the same copy.

Add-ons from GitHub

Your own Odoo modules, kept in a repository and synced onto the site.

On a site's page, connect a Git repository and branch. The platform clones it onto the server, links every module it finds onto Odoo's add-ons path, and restarts the site so the modules appear in Apps. Press sync again whenever the branch moves; a webhook can do it for you on every push.

Python packages your modules need

If a module imports something the Odoo image does not ship — pandas, openpyxl, a vendor SDK — put a requirements.txt at the root of the repository. Those packages are installed into the site's own package directory before Odoo loads the modules, and they survive the container being rebuilt.

A missing dependency is not a graceful failure

A module that cannot import aborts Odoo's registry, and every page of the site then returns an error. Declaring the requirement is how you avoid finding that out in production.

Domains and HTTPS

Every site gets an address on the platform domain. Your own domain takes one DNS record.

  1. Point the domain at the server. Create an A record for your domain pointing at the server's IP address, at your DNS provider.
  2. Add it in OdooLaunchPad, on the Domains page or the site's own page.
  3. Wait for the certificate. Once the domain resolves to the server, a Let's Encrypt certificate is issued automatically and nginx starts serving HTTPS on it.

DNS first, certificate second

Let's Encrypt proves you control the domain by reaching it over the public internet. If the record has not propagated, the certificate cannot be issued yet — that is not a failure, just the order things happen in. Verify the domain again once DNS has caught up.

A site can hold any number of domains; each gets its own HTTPS virtual host pointing at the same Odoo.

Staging

A copy of a live site to try things on, with a way to put the code back.

Creating a staging environment clones a production site — database, files and add-ons — into a second site of its own. You can break it freely. When the change is good, merging takes the code back to production; it does not copy the staging data over your live database.

In the Sites list, a staging copy is indented beneath the site it came from and marked Staging. That nesting is deliberate: the risk with staging is acting on the wrong one of two sites whose names differ by a word.

Order matters when deleting. A staging copy can be removed on its own. Production cannot be removed while a staging copy of it still exists — delete the staging site first.

Backups and restores

A backup is one compressed archive holding the database dump and the filestore.

Where backups go

Every organization gets platform storage by default — storage the platform runs, included with your plan. You can add your own destination instead (cPanel/FTP, DigitalOcean Spaces, or any S3-compatible bucket) under Backups → Destinations. When a backup policy names no destination, it uses platform storage.

Scheduling

A policy says three things: how often, from what time, and in whose clock. The cadence can be every 1, 2, 4, 6, 8 or 12 hours, or daily, weekly or monthly. "Every 6 hours from 02:00" means 02:00, 08:00, 14:00 and 20:00.

Set the timezone. The quietest hour of the night is a local idea, and it is the whole reason backups are scheduled for it. Policies default to your browser's timezone; older ones are in UTC.

Retention keeps the most recent backups and prunes the rest, so a schedule does not fill your storage indefinitely.

Restoring

Pressing Restore asks where it should go.

Put this site back

Replaces the site's own database and files with the backup. Anything since that backup is lost. This is the undo button.

Restore into another site, as a copy

Puts this data onto a different site — to test an upgrade against real data, refresh staging, or recover onto a replacement.

Restoring onto a different site destroys whatever that site holds, so it asks you to type the name of the site being replaced — not the backup — and it takes a rollback snapshot of the target first.

Versions must match

An Odoo dump only loads into its own major version. Restoring a 17.0 backup onto an 18.0 site is refused, and for good reason: it would not error, it would start migrating the schema on first boot and leave a half-converted database whose only dump is the one just consumed.

Version upgrades

One major version at a time, on a copy, with production untouched until you say so.

  1. Pick a running site. The target is always the next major version — 18.0 goes to 19.0, never straight to 20.0.
  2. The platform clones it to a staging copy and runs the migration there, using OpenUpgrade. Production keeps serving throughout.
  3. Check the migrated copy. It is a real site; sign in and look at the data.
  4. Promote when you are satisfied. The production domain starts serving the migrated site, and the old one is kept so you can roll back.

Rolling back returns the domain to the original site with its data intact. Discarding deletes the migrated copy and leaves production exactly as it was.

Bringing a site in

Migration takes a backup from another Odoo host and restores it into a site here.

  1. Upload the backup .zip on the Migration page. It is inspected on arrival — version, edition, modules and size are read out of the archive itself.
  2. Choose a target: an existing site, or let the platform create one for you first.
  3. Run the migration. Restoring into a site that already holds data requires explicit confirmation, and a rollback snapshot is taken before anything is overwritten.

Backups from Odoo 15.0 onwards are accepted, which is wider than the versions the platform will install new. That is deliberate: the archive describes somebody else's site, and refusing to let you say "16.0" would not make it a newer backup.

Your team

Roles are named sets of permissions, and each role holds everything the one below it does.

Invite colleagues from Team in the account menu. Each member gets a role, and the role decides what they can do. Senior roles always include everything junior ones have — that is structural, so it cannot be broken by a configuration mistake.

RoleSeesCan, in addition to the role above
Org userTheir own workView sites and their logs, view backups
DeveloperTheir own workCreate and manage sites, add-ons, staging; take backups; run migrations
Org managerThe organizationCreate and manage servers, attach domains, restore backups, configure schedules
Org adminThe organizationOrganization settings, billing, API keys, invite members and set roles
Org ownerThe organizationEverything, including deleting servers, sites, backups and members

Deletion sits with the owner everywhere in the product. That is a default a platform administrator can change, not a law.

Removing somebody

Deactivating keeps a person on the team list and stops them signing in — right for somebody who will be back. Removing ends their membership entirely and they disappear from the list. Their account is not deleted, because one email can belong to several organizations; inviting the same address adds them back.

You cannot remove yourself. The moment it succeeded you would have no role in the organization and could not put yourself back — somebody else would have to, and if you were the only owner, nobody could.

When something breaks

The site shows 502 Bad Gateway

nginx is up but cannot reach Odoo. Usually the container is still starting — give it a minute. If it persists, open the site's logs: Odoo prints why it refused to start, and a module that cannot import is the most common reason.

The site says Running but will not load

Check the server, not the site. If the server is offline or unreachable, every site on it is affected and the site's own status is stale.

HTTPS is not working on my domain

The certificate cannot be issued until the domain resolves to the server. Confirm the A record points at the right IP, wait for propagation, then verify the domain again.

Odoo says my database has expired

An Enterprise database without a valid subscription stops serving when its trial ends. Register your subscription code on the site's page. If the code is refused, the site will say so — Odoo decides, not the platform.

I cannot delete a server

Two things refuse it. Deletion protection is a lock an owner can switch on; only an owner can switch it off. Separately, removing the record of a machine that is still live at the provider is refused once, so you read the warning that the machine will keep running and billing — confirm again and it goes ahead.

Delete Record and Destroy are different. Delete Record removes OdooLaunchPad's record and leaves the machine alone. Destroy terminates the machine at the provider. For a server imported from elsewhere, only Delete Record is offered: the platform will not terminate a machine it does not own.

Part two — How OdooLaunchPad works

The four services

One dashboard in front, four backends behind it, sharing one JWT secret.

ServiceStackOwns
olp
odoo-launch-pad-backend/olp		 Spring Boot, MySQL, Flyway, Kafka, Redis Identity: organizations, users, roles and permissions, JWTs, 2FA, social login, billing and plans
prov-api
launchpad_prov_api		 Spring Boot, PostgreSQL, Flyway, Terraform, Ansible The core: servers, sites, domains, staging, upgrades, monitoring, alerts, the catalog
migration-api
launchpad_migration_api		 Node, Express, Sequelize, ssh2 Backups, backup destinations, schedules, restores, migrations in
notification
…/notification		 Spring Boot, Kafka consumer Turns olp's events into email
frontend
launchpad_Frontend_V1		 React, Vite, TypeScript, React Query, STOMP The dashboard

prov-api and migration-api share one PostgreSQL database. prov-api's schema is owned by Flyway; migration-api's Sequelize owns only the migration_* tables in that same database and never touches the rest. That is why migration-api can read a site's Odoo version directly and why a schema change on either side has to respect the other.

Identity and tenancy

olp signs access tokens; prov-api and migration-api validate them with the same secret. If those drift between services, logins succeed and every subsequent request 401s.

The organizationId claim is the tenant id. Every query in prov-api and migration-api is scoped by it. A resource belonging to another organization reads as absent rather than forbidden, so an endpoint cannot be used to discover which ids exist.

The token also carries the holder's permissions, as codes such as bak.restore or srv.delete. Every door asks for a permission rather than a role name. This replaced thirty hand-written role lists that had drifted apart — at one point an organization's owner could not restore their own backup, because the route listed three roles and ownership was added to the product after they were written.

Belonging to more than one organization

One email can hold memberships of several organizations with a different role in each. Switching re-scopes the session: a new token is minted carrying the role held there, and that organization's entitlements. Nothing about the account changes — only which organization the session is acting in.

Provisioning

Terraform makes the machine, Ansible prepares it, shell scripts over SSH do everything after that.

  1. Terraform creates the machine in the customer's own cloud account, using credentials they connected.
  2. Ansible installs Docker, PostgreSQL, nginx, certbot and the firewall rules, and starts a shared PostgreSQL container on a private Docker network.
  3. Per-site scripts run over SSH for everything afterwards: creating a site, removing one, switching edition, upgrading, syncing add-ons, cleaning disk.

Long operations run in the background and report progress over websockets, so the dashboard shows a live status rather than a spinner. Every run writes a log file named deterministically after the operation and the site, which is what the dashboard's log viewer reads.

Where the work actually happens

Nothing executes on the platform's own servers. Scripts are streamed to the customer's machine over SSH stdin and run there, so the platform holds no copy of a customer's data in transit and a backup's bytes go from the customer's server straight to the storage destination.

Anatomy of a site

What exists on the server once a site is running.

/opt/odoo/instances/<name>/
├── config/odoo.conf        the Odoo configuration, mounted read-only
├── data/                   filestore + sessions  (Odoo's data_dir)
├── extra-addons/           add-ons cloned from Git
└── python-packages/        pip packages installed with --target

The container is named odoo-<name> and joins the shared odoo-net Docker network, where PostgreSQL is reachable simply as postgres. Odoo's HTTP port 8069 and longpolling port 8072 are published to host ports allocated per site; nginx proxies the public domain to the published HTTP port.

The configuration

[options]
db_host = postgres
db_name = odoo_<name>
db_filter = ^odoo_<name>$
admin_passwd = …
proxy_mode = True
http_interface = 0.0.0.0
addons_path = /mnt/enterprise,/mnt/extra-addons,…

Two settings that are not optional

proxy_mode tells Odoo to trust the headers nginx forwards, since nginx terminates TLS. http_interface must be 0.0.0.0: Odoo 20 changed its default to loopback, and inside a container that means the published port forwards to nothing — nginx returns 502 while Odoo logs a perfectly clean start.

File ownership differs by version

The user Odoo runs as inside its image is not the same across versions: Odoo 17 runs as 101:101, Odoo 18 and later as 100:101. Anything written into the site's directories has to match, or Odoo cannot write its own sessions and every request fails.

Backup architecture

A backup is one archive containing a pg_dump of the database and a tar of the filestore. One archive means one object in storage, which keeps object counts — and an FTP account's inode limit — a long way from mattering.

Destinations

A destination is either cPanel/FTP or S3-compatible. DigitalOcean Spaces is S3, so it needs no separate backend — only the right endpoint, which is derived from the region so the two cannot disagree. Destinations belong either to the platform (shared, the default for every organization) or to one organization.

Reading a backup later

Every backup records the destination that wrote it. Downloads, restores and deletions resolve that destination, not whichever one is current. Changing where backups go retires the old destination rather than overwriting it, so archives already stored stay reachable with credentials that still work.

Scheduling

The scheduler asks "when should this last have run, and has it?" rather than "is it that hour now". A tick that lands late still fires; one that lands twice does not fire twice; and an hour missed because the service was restarting is caught up rather than lost.

Imported servers

A machine the platform did not build can be brought under observation without being touched.

Takeover inspects a running server over SSH — reading only, with no file written — records what it finds, and leaves it Observed. The sites on it are marked externally managed. In that state the platform monitors and nothing else: starting, stopping, reprovisioning and destroying are all refused.

Promoting a server moves it to Managed and lifts those refusals. Destroy is refused outright until then, because an imported machine is somebody's live server that the platform merely wrote down, and terminating it is the one act that could never be undone.

Delete Record always works. A record is a description, and keeping one of something nobody can reach serves nobody. Forgetting a server also forgets the records of its sites; the sites themselves keep running.

Alerts and the audit trail

Alerts are opt-in per organization, per type. Nothing fires until somebody switches it on, which is why a new organization is quiet. Each type can go to email, SMS or a webhook independently. An alert that was suppressed is recorded as suppressed, because from the outside that looks identical to one that failed to send — and that is the question support actually gets asked.

Removals are also written down. Deleting a site or forgetting a server records who did it, what it was and when, and raises an alert naming the person. Creations are recorded but not emailed: whoever made it already knows, and a message for every new site trains people to ignore the ones that matter.

Deployment

All four services and the dashboard run in one k3s cluster, in a namespace per environment. Deployments are image-tag updates onto deployments that already exist; a structural change — a new environment variable, different resources — means editing the manifests and re-running the bootstrap.

Gates

main is hard-gated: failing tests for a changed module block the production deploy. dev is soft-gated, so a red suite is visible but does not stop iteration — which means a change that reddens the suite stalls at the dev-to-main merge instead.

Never edit an applied migration

Flyway records a checksum for every migration it has run. Changing one that has already been applied — even a comment — makes Flyway refuse to start against a history it no longer recognises, and the pod crash-loops. Add a new migration instead.

Caching

Assets are content-hashed and served immutable for a year; index.html is served no-store. That pairing is what makes a deploy reach people: the entry point is the only file that names the hashed bundles, so if it is cached, browsers keep loading the previous build indefinitely.
